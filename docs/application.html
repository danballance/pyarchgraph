Package 02 / pyarchgraph.application

Application

Organises one analysis, from the request through collection and checks to the final report.

11 modules27 classesWalkthrough + class index

Its role

The application turns a caller's choices into an organised analysis run. Its incoming port is ProjectAnalyzer.analyse(request); AnalyseProject implements that workflow.

Accept a request

Validate source roots, options, and the selected gate before collection.

Coordinate the work

Collect sources through ports and call domain rules in the required order.

Assemble a report

Bring coverage, view results, and findings together for the caller.

Filesystem access, parsing, and graph-library operations arrive through injected collaborators. The application itself performs no external I/O. This allows the same workflow to run with real adapters or in-memory substitutes.

Follow a request

A caller supplies demo as the source root, its parent as the base directory, and the default analysis options.

  1. Validate and locate

    OptionValidator checks the request and options. ProjectAccess then locates the roots and base directory. Invalid requests stop before source discovery or metadata access.

  2. Collect a catalogue

    SourceCatalogBuilder asks SourceDiscovery for sources and ImportFactSource for drafts. It applies shared report paths and source IDs, reconciles bindings across roots, and asks the domain canonicaliser to assign fact IDs. The result is one SourceCatalog.

  3. Resolve and assess scope

    AnalyseProject combines discovered and configured targets, calls the import resolver, and gathers coverage diagnostics. LayoutDiagnosticService uses project observations to flag questionable root choices without changing the selected roots.

  4. Run registered views and checks

    The use case builds an AnalysisSnapshot. StrategyEngine normalises it, builds and validates each registered view, prepares its cycle analysis, and runs its selected checks. It attaches check IDs to findings and creates a ViewReport for each view.

  5. Return the assembled report

    The domain coverage policy determines completeness. AnalyseProject combines sources, coverage, and all view reports in an AnalysisReport. The configured analyser can be reused; each run keeps its observations separate.

The catalogue holds collected sources and facts. The snapshot supplies the analysis shared by views. The report holds the completed results. Each has a different job in the workflow.

Reports and failures

For the example, report.status is complete, while every built-in view contains a cycle error finding. The default gate is structural, and report.selected_view gives convenient access to that view's report.

What the caller receives
SituationApplication outcome
No error diagnostics or unacknowledged boundariesA complete report, which may still contain check findings.
A selected source cannot be read or parsedAn incomplete report with source diagnostics and any recovered results.
A referenced boundary is unacknowledgedAn incomplete report showing the missing implementation coverage.
Invalid request or analysis setupA validation error, such as AnalysisError or ValueError, rather than a report.
A registered view or check fails validation or raisesExtensionError identifies the failing extension; no report is returned.

StrategyRegistry names the available views and checks and selects checks per view. Custom strategies use the same workflow and result validation. An empty check selection leaves coverage requirements in place; cycle counts are still computed for the view.

The application returns Python values. The CLI adapter is responsible for JSON presentation and exit codes. Changing the gate selects which findings determine the CLI result; it does not reduce the coverage requirements.
